2.2 MoE Layer 詳細步驟（Layer 3–77）

Step F-1：Router（輕量，常駐 HBM）

# W_router 是小矩陣（6144×256），常駐 HBM
router_logits = x @ W_router       # [B, 6144] @ [6144, 256] → [B, 256]

# scoring_func = "sigmoid"（GLM-5.2 特有，非 softmax）
scores = sigmoid(router_logits)

# topk_method = "noaux_tc"
top8_scores, top8_indices = topk(scores, k=8)  # 選最高的 8 個 expert

# norm_topk_prob = true
top8_weights = normalize(top8_scores)  # 加權係數

Step F-2：Shared Expert（BF16，常駐 HBM，永遠執行）

# 不受 Router 控制，每層都必定執行
shared_out = shared_expert_ffn(x)  # BF16，直接從 HBM 讀取

Step F-3：Routed Expert 計算 ← CPU Offload 發生點

for expert_idx in top8_indices:
    if expert_idx in HBM_cache:
        # 熱 expert：直接從 HBM 讀取計算（快）
        out_i = hbm_expert[expert_idx](x)
    else:
        # 冷 expert（根據框架選擇）：
        # vLLM：整層 H2D → GPU 計算
        # SGLang+KT：直接在 CPU 上計算（不 H2D）
        out_i = cpu_or_offload_expert(expert_idx, x)

Step F-4：加權合併

# routed_scaling_factor = 2.5（GLM-5.2 特有）
total_out = shared_out + sum(out_i * weight_i for i in top8) * 2.5

3CPU Offload 機制說明

3.1 術語

H2D — Host to Device

CPU RAM（LPDDR5X）→ GPU HBM
把資料從主記憶體搬到顯卡

D2H — Device to Host

GPU HBM → CPU RAM（LPDDR5X）
把資料從顯卡搬回主記憶體

3.2 為什麼需要 CPU Offload

現有 TP=2（無 offload）

每 GPU 負責 128 experts
模型 weights：224 GB / GPU
剩餘 KV Cache：~19 GB（偏少）

啟用 Offload（64 hot experts/GPU）

模型 weights：133 GB / GPU
剩餘 KV Cache：~84 GB（4× 提升！）
冷 experts 移至 LPDDR5X

5vLLM 的 CPU Offload 實作

5.1 --cpu-offload-gb 的真實機制

💡 重要釐清：--cpu-offload-gb 卸載的是模型權重（Model Weights），不是 KV Cache。機制為 Layer-level（整層），非 per-expert 粒度。
vLLM Layer-Level Offload 流程（PR #6496 + #29941）：
Idle 時部分 layer weights 存放在 CPU pinned memory（LPDDR5X）
Forward Nlayer N weights：CPU → GPU（H2D prefetch，async）
Compute NGPU 執行 layer N 的計算（同時 prefetch layer N+1）
Evict N-1layer N-1 weights：GPU → CPU（D2H evict，async）

5.2 Layer-level Offload 對 MoE 的根本問題

❌ vLLM Layer-Level Offload
1Router → top-8 indices
2H2D：整層 256 experts × 18.87 MB = 4.78 GB！
3GPU 計算 8 個 experts（151 MB 實際有用）
4D2H：整層搬回 CPU
無效傳輸：96.9%（4.63 GB 白費）
✅ 理想的 Per-Expert Offload
1Router → top-8 indices
2查詢 HBM cache，識別 hot/cold experts
3H2D：只載入冷 experts（按需）
4GPU 計算 hot experts + 冷 experts
H2D 傳輸量：僅需要的部分（vLLM 尚未實作）

5.3 建議參數（EGM Enable 環境）

vllm serve /models/afsbox/nvidia/glm5.2-nvfp4/latest \
  --max-model-len=131072 \
  --max-num-seqs=128 \               # 從 64 提升（KV Cache 更充裕）
  --tensor-parallel-size=2 \
  --gpu-memory-utilization=0.80 \    # 從 0.95 降低，釋放空間給 offload
  --cpu-offload-gb=32 \              # 允許 32 GB offload 到 LPDDR5X
  --max-num-batched-tokens=32768 \
  --kv-cache-dtype=fp8 \
  --speculative-config.method=dspark \
  --speculative-config.num_speculative_tokens=7 \
  --enable-prefix-caching \
  --load-format=runai_streamer \
  --model-loader-extra-config='{"memory_limit":0}'
💡 預期效果：HBM weights ≈ 210 GB（節省 ~33 GB）；KV Cache ≈ 50 GB（從 19 GB 提升 2.6×）；推論速度輕微下降（prefetch pipeline 掩蓋大部分延遲）。

6SGLang + KT-Kernel 的改良

6.1 核心改良：Per-Expert 粒度 + CPU 直接計算

SGLang + KT-Kernel 的 CPU-GPU 混合推論：

  GPU HBM                              CPU LPDDR5X
  ┌────────────────────┐               ┌────────────────────┐
  │  Hot Experts       │               │  Cold Experts      │
  │  （高頻被選中）      │               │  （低頻被選中）     │
  │  直接在 GPU 計算    │   並行執行    │  直接在 CPU 計算    │
  │  （從 HBM 讀取）    │◄────────────►│  （AMX/SVE2 GEMM） │
  └─────────┬──────────┘               └─────────┬──────────┘
            │           加權合併兩側輸出           │
            └──────────── → GPU（只傳結果） ───────┘

  關鍵差異：冷 expert 不 H2D！直接在 CPU 上算完再傳小結果。

6.2 四種 Expert 調度策略

策略說明適用場景
uniform每層均勻分配 N 個 GPU expert預設，無需統計資料
frequency把最常被激活的 expert 放 GPU最佳效能，需預先收集統計
front-loading從第一層開始填滿 GPU測試基準

🔄 動態更新（--kt-enable-dynamic-expert-update）：Prefill 階段統計激活頻率，自動將高頻 expert 換到 GPU HBM，提升後續 decode 的 GPU 命中率。
